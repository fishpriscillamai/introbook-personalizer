# 检索与来源核验

唯一配置：[knowledge-sources.json](knowledge-sources.json)。已验证组织 MH & MD；案例在“官网后端数据/客户案例知识库”，方案在“明道云知识库/解决方案知识库”。禁止改用同应用的企业销售知识库或测试知识库。

## 宿主接入

需要 HAP Personal MCP 的 `get_app_knowledge_list`、`knowledge_search`、`get_record_details`，必要时 `get_record_relations` / `get_worksheet_structure`。名称前缀可能不同，按当前工具的能力和实际参数匹配。无工具或权限时明确指出缺少连接或读取授权；不向用户索取凭据粘贴进文件，也不切换到另一套令牌。

首次使用先用配置中的 appId 和 knowledgeId 检查可读性；库被移除、权限拒绝或返回错误时不能假装空结果，更不能据此捏造案例。无需批量下载整个库。

## 流程

1. 在建立本次工作副本后执行 `search-plan --request request.json`，取得两次只读调用参数。query 保留行业、完整业务概念和场景修饰；不包含无必要的客户机密。两应用分别查询，默认 hybrid、topK 8、types=record/record_attachment。
2. 阅读结果，优先同品牌、同业务场景和同行业证据。分别选择 2–3 个案例与 2–3 个伙伴解决方案。可补一轮更明确的查询；跨行业结果须说明可借鉴机制，不冒充同行业。
3. 对每个拟使用结果，以其 appId、worksheetId、rowId 调用 `get_record_details` 回读当前原记录。附件召回须回读所属记录；原记录不可读则不采用。核验伙伴公司全称以用于方案副标题；需要收益等明细时读取关联记录核对，不把检索切片当完整事实。
4. 案例状态必须为“发布中”（key=10）；方案必须为“公开上架”。内部上架、编辑中、已下架、不可公开等均排除，不能通过匿名处理绕过。
5. 用 `normalizeSource(kind, liveResponse)`（scripts/knowledge.mjs 导出）提取必要公开字段，保存至本次 sources.json。kind 为 cases 或 solutions。函数会丢弃人员、联系方式、下载地址等字段；不要先将原始响应写入仓库或工作日志。若宿主只能调用命令行，可将必要字段白名单组成 JSON 从 stdin 传给 normalize-source。
6. 把“为什么相关、支撑哪段改写/哪个案例、哪些数字与引语有依据”写入内部 source-notes.md；不要把内部追溯内容嵌入客户 HTML。量化结果需保留原指标、方向、数值、口径及公开原文；实施点位数、系统数等规模不冒充改善结果。补充细节需同时保留公开原文依据和来源 ID；函数默认只摘录 overview/challenge/solution 段落，不能以未摘录的数字直接生成成果。

hybrid 的 score 是排序信号，不是可信度或百分比。没有严格同行业案例时可扩大到同场景跨行业案例并明确标注借鉴点；数量仍不足时记录缺口，不能降低公开状态要求。

sources.json 中 verifiedAt 必须是本轮生成开始后的真实回读时间。CLI 不会自行连接 MCP；来源真实性和语义适配由宿主实际读操作及人工/AI 内容核验完成，脚本负责结构、状态、品牌、时间和引用完整性校验。

跨语言输出优先使用已公开的对应语言内容；翻译中文案例/方案时保留原文、来源状态与指标口径。公司名称如无已核验的官方英文名称，可采用可追溯的译写并内部记录原名、译名和“未独立核验注册英文名”，不可把译写冒充新的公开事实。数值与方向不得因翻译改变。
